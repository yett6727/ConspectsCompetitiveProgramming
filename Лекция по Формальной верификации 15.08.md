	Верификация - проверка объекта на соответствие требованиям
	В контексте программирования верификация программы - проверка поведения программы на соответствие предъявленным требованиям

Самый простой способ проверки программы - тестирование, то бишь проверка соответсвия вывода программы на тесте
Проверка самого кода программы называется в профессиональной среде экспертной оценкой

К сожалению тестирование - не очень хороший способ верификации, например потому, что невозможно перебрать все входные данные

Кроме того, в случае если есть тесты, то можно просто их все заифать XD
Да и вообще, тест - проверка точки, так что даже достаточно плотное покрытие возможных входов тестами не даст стопроцентной защиты

Язык программирования rocq позволяет писать программы а также дает инструменты для верификации программ

Попробуем примерно представить себе работу программы аппарата для лучевой терапии
```rocq
Variant Beam := Off | Low | High. //сила излучение
Variant Shield := Down | Up. //состояние системы защиты пациента от излучения

Record State := { //состояние аппарата описывается двумя переменными
	beam : Beam;
	shield : Shield;
}
```
Добавим команды
```rocq
Variant Command := 
	ShieldUp | 
	ShieldDown | 
	BeamOff | 
	BeamLow | 
	BeamHigh.
```
Теперь опишем исполнение команд функцией, принимающей аргументы Command и State и возвращающее State
```rocq
Definition exec (c : Comand) (s : State) : State :=
	match c with 
		| ShieldUp == {|
			beam := beam s;
			shield := Up;
		|}
		| //<...>
		| BeamHigh{|
			beam := High;
			shield := shield s;
		|}
		| _ => s // любые другие команды ничего не поменяют
end.
```
Попробуем описать безопасность состояния луча для человека
```rocq
Definition safe (s : State) : Prop :=
	beam s = High -> shield s = Up.
```
Наша функция будет возвращать тип данных Prop, как утверждение

Потребуем исполнения теоремы: если исходное состояние безопасно, то после исполнения команды, оно останется безопасным.

Изначальное состояние считаем Beam = Off, Shield = Down, то бишь оно безопасное.
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
```
После запуска этого кода мы получим как текущую цель верификации кода доказзательство теоремы

Докажем теорему перебором всех вариантов
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
```
Теперь мы получим context состоящий из s : State и c : Command, фактически мы выполнили действие "рассмотрения произвольных s и c".
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c Hs.
	destruct c.
```
Теперь мы получим 5 целей, каждая из которых содержит различные состояния c
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
	destruct c.
	- simpl.
	  unfold safe.
	  simpl.
	  reflexivity.
```
Однако для первого случая доказательство простое, так что система одобряет тот факт, что мы приняли рефлексивность.
Также мы можем сделать так:
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
	destruct c.
	- easy.
```
Все простые случаи легко разбираются
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
	destruct c.
	- easy.
	- easy.
	- easy.
	- easy.
	- easy. //здесь не сработает так как это случай b : High, s : Down
```
Попробуем исправить баг, так как команда ведет себя неправильно и не выполняет теорему сохранения состояния всегда безопасным

Так что rocq говорит, что необходимо пересмотреть логику
Здесь можно применить разные дизайны, например в случае попытки включить луч форсить поднятие щита или выключать луч в случае выключения щита
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
	destruct c.
	- easy.
	- easy.
	- easy.
	- easy.
	- simpl.
	  unfold safe in *.
	  simpl.
	  destruct (shield s) eqn:E.
```
Теперь мы увидим что разбор программой всех случаев
Программа покажет что в контексте есть неверное утверждение, из-за чего возникнет проблема - из лжи следует что угодно.
```rocq
Theorem exec_is_safe : \forall s c,
	safe s -> safe(exec c s).
Proof.
	intros s c.
	destruct c.
	- easy.
	- easy.
	- easy.
	- easy.
	- simpl.
	  unfold safe in *.
	  simpl.
	  destruct (shield s) eqn:E.
	  + intros Hb.
		apply Hs in Hb.
		inversion Hb.
	  + easy.
Qed.

Print exec_is_safe
```
Теорема доказана, и rocq ее одобряет, значит она верна

Попробуем доказать теорему: Любая последовательность команд будет безопасной.
```rocq
From Stdlib Require Import List.
Import ListNotations.

Definition Program := list Command.

Check [ShieldUp; BeamOff].

Fixpoint run (p : Program) (s : State) : State :=
	match p with
	| [] => s
	| c :: p` => 
run p' (exec c s)
end.

Theorem run_is_safe : \forall p s, safe s -> (run p s).
Proof.
	induction p. //индукция по программе p
	- easy. //случай где программа пустая
	- //случай где программа имеет голову a
```
во втором случае система создала предположение IHp, которое необходимо доказать
```rocq
Theorem run_is_safe : \forall p s, safe s -> (run p s).
Proof.
	induction p. //индукция по программе p
	- easy. //случай где программа пустая
	- intros s Hs.
	  simpl.
	  apply IHp.
	  apply exec_is_safe.
	  easy.
Qed.
```
Теперь из нашей теоремы напрямую следует доказанная по индукции теорема, что любой набор программ будет верным

Таким образом для любого набора входных данных мы доказали верность выполнения программы, а в общем случае такая цель недостижима тестированием, а значит формальная верификация программ сильно безопаснее более дешевых методов верификации.
